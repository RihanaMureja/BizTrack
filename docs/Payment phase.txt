You need a real subscription payment system so business owners pay BizTrack before or while using the system. Chapa or SantimPay would act as the payment gateway. BizTrack should create the subscription invoice, send owner to payment, receive callback/webhook, verify payment, then activate/extend the business subscription.

I’ll describe it using Chapa because its docs are public and clear. SantimPay would follow the same architecture: initialize payment, redirect user, receive callback/webhook, verify payment, update subscription.

Sources checked:
- [Chapa verify payments](https://developer.chapa.co/integrations/verify-payments)
- [Chapa webhooks](https://developer.chapa.co/integrations/webhooks)
- [Chapa developer docs](https://developer.chapa.co/)

**How Payment Should Work**
1. Super admin creates subscription plans.
2. Business owner chooses a plan.
3. BizTrack creates a local subscription payment record.
4. BizTrack calls Chapa/SantimPay API to initialize payment.
5. Gateway returns checkout URL.
6. Owner is redirected to gateway checkout.
7. Owner pays with Telebirr/card/bank/mobile money depending on gateway.
8. Gateway redirects owner back to BizTrack callback URL.
9. Gateway also sends webhook/IPN to BizTrack.
10. BizTrack verifies the payment with the gateway API.
11. If verified:
   - Mark payment as completed.
   - Activate or extend business subscription.
   - Save gateway reference.
   - Notify owner.
   - Log audit event.
12. If failed/cancelled:
   - Mark payment failed.
   - Keep business unpaid/pending.

**Important Rule**
Never trust only the browser redirect.

The browser callback is useful for showing “Payment pending/successful,” but the real activation must happen after server-side verification or webhook verification.

**Recommended Architecture**
Create a separate payment flow for platform subscriptions. Do not mix it with the existing `payments` table used for customer sale payments.

Current `payments` table is for business sales/POS payments.

For BizTrack subscription payments, create a new table.

**Chapa Integration Flow**
Chapa has two important operations:

1. Initialize transaction.
2. Verify transaction.

Chapa verify endpoint:

```text
GET https://api.chapa.co/v1/transaction/verify/{tx_ref}
```

Header:

```text
Authorization: Bearer CHAPA_SECRET_KEY
```

When starting payment, BizTrack should send:
- amount
- currency
- email
- first_name
- last_name
- phone_number
- tx_ref
- callback_url
- return_url
- customization title/description

`tx_ref` must be generated by BizTrack and must be unique.

Example:

```text
BT-SUB-{business_id}-{timestamp}
```

**Best Database Design**
Add two new tables:

```text
subscription_payments
business_subscriptions
```

`subscription_payments` tracks money.

`business_subscriptions` tracks access period.

This is cleaner than only storing `subscription_id` on `businesses`.

**How Activation Should Work**
When owner pays successfully:

```text
subscription_payments.status = completed
business_subscriptions.status = active
business_subscriptions.starts_at = now()
business_subscriptions.expires_at = now() + subscription.duration_months
businesses.subscription_id = selected subscription
```

Then `EnsureSubscriptionIsActive` middleware checks:

```text
Does this business have an active subscription that has not expired?
```

If yes, allow access.

If no, redirect owner to subscription payment page.

**Approval vs Payment**
You need two gates:

1. Business verification approval.
2. Active paid subscription.

Recommended access logic:

```text
Owner signs up
    ↓
Submits business verification
    ↓
Super admin approves business
    ↓
Owner selects subscription and pays
    ↓
Payment verified
    ↓
System modules unlock
```

Or if you want payment before approval:

```text
Owner signs up
    ↓
Submits verification
    ↓
Selects plan and pays
    ↓
Super admin approves business
    ↓
System modules unlock
```

I recommend approval first, payment second, because you avoid taking money from rejected businesses.

**Middleware Logic**
You already have:

```text
EnsureBusinessIsApproved
EnsureSubscriptionIsActive
```

Use both for core modules:

```php
Route::middleware(['business.approved', 'subscription.active'])->group(function () {
    // products, inventory, sales, reports, etc.
});
```

Business Profile and Subscription Payment pages should remain accessible before subscription is active.

**Webhook Logic**
Webhook controller should:

1. Receive gateway payload.
2. Verify signature.
3. Find local payment by `tx_ref`.
4. Call gateway verify API again.
5. Compare:
   - amount
   - currency
   - tx_ref
   - status
6. If valid and not already completed:
   - mark payment completed
   - activate subscription
   - notify owner
   - audit log
7. Return HTTP 200.

This must be idempotent, meaning repeated webhook calls should not duplicate subscription periods or duplicate records.

**Security Rules**
Do not:
- trust frontend payment success
- store API secret in frontend
- activate subscription from callback only
- allow amount from browser without checking subscription price
- process same webhook twice
- skip signature verification

Do:
- generate `tx_ref` server-side
- calculate amount from subscription table
- verify payment server-side
- store raw gateway response
- compare amount/currency/status
- make webhook idempotent
- log all payment state changes

Test:

**Best Choice**
Use Chapa first.

Reason:
- It supports Ethiopian payment methods including Telebirr.
- It has clear transaction initialization, verification, and webhook flow.
- It is suitable for SaaS subscription payment collection.

SantimPay can be added later using the same `PaymentGatewayInterface`, so the rest of BizTrack does not need to change.
